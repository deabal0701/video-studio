# 11 — 상용 품질 루프 (클래스 전수 감사 → 졸업 순회)

> **역할**: 이 루프를 도는 세션은 Video Studio 의 **기획자이자 화면 디자이너**다.
> 목표는 상용 서비스 수준 — 쉽게 쓰이고, 깔끔하고, 다음 행동이 항상 보이는 화면.
> (2026-08-22 사용자 지시: "무한하게 반복하여(24시간) 보완을 계속할 수 있는 loop")
>
> **2026-08-23 프로토콜 개정 (71회차 후 — 사용자 지시)**: 화면 순회(1회차 = 1화면)는
> 같은 결함 클래스를 화면 수만큼 반복 발견해 수렴이 느렸다 — 대비 검사 누락이
> 53→66→68회차에서 3번, 0개 상태 오판이 65→67회차, 잠금 구멍이 52·56·58·59·60·61
> 여섯 회차에서 "같은 구멍"으로 나왔다. 개념 결함 1개 = 화면 결함 N개인데 하나씩
> 주웠던 것. 이제 **모드 A(클래스 전수 감사)** 로 한 클래스를 전 화면에서 한 번에
> 소탕하고, **모드 B(졸업 순회)** 로 수렴을 확인하며, **종료 기준**으로 루프를 끝낸다.

## 모드 A — 클래스 전수 감사 (1회차 = 결함 클래스 1개 × 전 화면)

70회차의 기록에서 추출한 반복 클래스. 위에서부터 순서대로 한 회차에 하나씩:

| 클래스 | 찾는 법 (전수 후보 추출) | 원 회차 |
|---|---|---|
| **A1 조용한 실패** — 실패가 아무 말 없이 삼켜짐 | `grep -rn "fail=lambda" app/` + 실패 콜백이 화면에 사유를 쓰는지 전수 대조 | 30·70 |
| **A2 이중 실행 잠금 구멍** — 재클릭이 중복 잡·중복 생성 | 잡 제출·저장·생성·삭제 버튼 핸들러 전수 목록 → 잠금(setEnabled/재진입 가드) 여부 표 | 52·56·58·59·60·61 |
| **A3 늦은 응답 되덮기** — 비동기 done 이 옛 대상/다음 화면을 덮음 | `run_bg` done 콜백 중 화면 상태를 쓰는 곳 전수 → 대상(eid·토큰) 가드 여부 표 | 58·59·60 |
| **A4 빈/0개/신규 상태** — 0을 완료·소진으로 오판, 자리표시자 노출 | 모든 페이지를 **빈 데이터 폴더**(0프로젝트)와 **갓 만든 프로젝트**(0영상·자리표시자)로 띄우는 프로브 → 문구 전수 눈검수 | 65·67·70 + baseUrl 결함 |
| **A5 개발자 용어 노출** — id·파일명·영문 상태어·은어 | 화면 문자열 리터럴 grep(`.html`·`_id`·영문 상태어) + 캡처 전수 눈검수 | P2 계열 다수 |
| **A6 결과 라벨 잔존** — 대상이 바뀌어도 앞 대상의 결과·오류가 남음 | 결과 라벨(저장됨·적용됨·오류) 보유 화면 전수 → load()/대상 전환 시 초기화 여부 표 | 52·53·54·58 |
| **A7 짝 파일 불일치** — 같은 것을 두 자료가 다른 이름·값으로 든다 (plan.md 템플릿 표 `intro·b1` vs scenes.json 골격 `hook·broll…` — 안 고친 채 [대본으로 반영]만 눌러도 골격에 없는 클립이 끼어든다) | 짝을 이루는 자료 전수 대조 — plan 템플릿↔scenes 골격, 위저드↔프로젝트 설정 기본값, 종류 스펙↔엔진 템플릿, 화면 표시명↔배포 문안. 대조 자체를 테스트로 고정 | 72(중단 회차)의 I-6 |

```
1. 클래스   아래 "클래스 커서"의 다음 클래스 하나를 잡는다
2. 추출     표의 "찾는 법"으로 전수 후보 목록을 만든다 (grep·프로브 — 추정 금지)
3. 판정     후보마다 결함/정상/해당없음 — 정상 판정에도 근거 한 줄 (자기반문 겸)
4. 수정     결함 전부를 이 회차에서 고친다. 같은 판단이 화면 2곳 이상에 있으면
            **core 로 승격**부터 한다 (contrast_report·episode_display_name 선례 —
            사본이 남아 있는 한 클래스는 재발한다)
5. 고정     이 클래스의 **불변식 테스트**를 남긴다 — 개별 회귀가 아니라 일반 규칙
            (예: "fail= 없는 run_bg 금지" 린트 테스트, "빈 데이터로 전 페이지를 띄워도
            금지 문구('완료'·'없습니다' 오판)가 없다" 프로브 테스트). 새 화면에도
            자동 적용되는 형태여야 클래스가 다시 안 자란다
6. 검증     pytest 전체 + 재캡처 눈검수 (기준은 종전 그대로 P1~P25·자기반문·판정 4항)
7. 기록     회차 기록에 "A# 클래스: 후보 N·결함 M·수정 M·불변식 테스트" + 커서 전진
8. 푸시     커밋 → origin/master (사용자 상시 지시) + 앱 재시작
```

## 모드 B — 졸업 순회 (모드 A 소진 후)

클래스 커서가 끝나면 종전 화면 순회로 돌아가되, **졸업 기준**을 적용한다:

- 화면 하나를 순서대로 점검 (종전 프로토콜: 캡처→P1~P25→자기반문→수정→검증→기록→푸시)
- **졸업**: 그 화면에서 **연속 2회차 P0~P2 무발견**(P3·문구 다듬기만 나옴)이면 그 화면은
  커서에서 제외한다. 발견되면 카운트는 0으로 되돌아간다
- **종료**: 전 화면 졸업 → 루프 종료를 회차 기록에 선언하고 멈춘다. 이후 품질은
  모드 A 가 남긴 불변식 테스트가 지키고, 새 화면·새 기능이 생기면 그 화면만
  커서에 복귀시킨다 (24시간 상시 순회는 하지 않는다 — 2026-08-23 개정)

**추정 금지 — 반드시 캡처를 눈으로 본다. 캡처 자체도 의심한다** (09 캡처 함정 표).
큰 설계 변경(구조 개편·기능 추가)은 루프에서 하지 않는다 — 10_ux-plan 에 제안으로 적고
사용자 결정을 받는다. 루프는 **다듬기**다. 결정 대기 제안(현재 12·13)은 루프가 못
지우는 항목이므로 회차 기록이 아니라 사용자에게 있다.

## 상용 기준 (P-체크 — 이 세션에서 사용자가 실제로 지적한 패턴의 일반화)

| # | 기준 | 원 지적 |
|---|---|---|
| P1 | **다음 행동이 화면에 보이는가** — 기억을 요구하지 않는다 | "어떻게 만들어야 할지 모르겠다" |
| P2 | **말이 담당자 언어인가** — 파일명·id·은어·개발 용어 금지 | "저장이 뭔가"·"이기고 있습니다"·"intro.html 을 어떻게 아나" |
| P3 | **간격이 숨을 쉬는가** — 폼 세로 ≥18px, 창 여백 ≥24px | "간격이 너무 작다" |
| P4 | **선택·상태가 눈에 보이는가** — checked·재생 중·진행 중 | "선택이 안 된다"·"중지를 어떻게"·"프로그레스바가" |
| P5 | **모든 문이 양방향인가** — 들어가면 나오는 길이 보인다 | "직접 쓰기 후 어떻게 돌아가나"·"①②③은 어디" |
| P6 | **좁은 창(1180px)에서도 안 깨지는가** — 가로 스크롤·잘림 금지 | "상단 틀이 안 맞는다" |
| P7 | **파괴적 동작이 보이면서 안전한가** — 삭제는 찾기 쉽고 확인을 거친다 | "삭제는 어디 있는가" |
| P8 | **재클릭·재진입이 동작하는가** — 이미 선택된 것을 눌러도 반응 | "대시보드 클릭해도 안 돌아간다" |
| P9 | **빈 상태가 말을 하는가** — 비어 있으면 무엇을 하면 되는지 | 09 G1 승계 |
| P10 | **입력이 쉬운 형태인가** — 자유 텍스트보다 콤보·프리셋·자동 생성 | "글자수 지정이 어렵다"·"id 자동으로" |
| P11 | **일관성** — 같은 개념은 같은 말·같은 위치·같은 모양 | "N강"↔"N편" 혼재 등 |
| P12 | **낭비 공간이 없는가** — 큰 빈 영역·중복 표시 | 09 G3·G5 승계 |
| P13 | **배치가 창 크기에 맞는가** — 내용이 좌상단에 몰리고 우·하가 크게 비면 위반. 콘텐츠 최대폭을 정하고 남는 폭은 의도적으로 배분한다 | "화면 사이즈에 비해 배치도 안 맞는다" (위저드 실측) |

**반복 확인 (52·53·54회차에서 연속 발견)** — 화면이 결과 라벨(저장됨·적용됨·경로 문제)을
들고 있으면 **대상이 바뀔 때 지우는지** 본다. 안 지우면 앞 프로젝트/앞 영상의 결과가
다음 화면에 그 대상의 것처럼 남는다 (대본 탭은 빨간 오류가 **다른 영상의 결함**으로 읽혔다).
같은 대상을 재로드할 때는 남겨야 한다 — 저장 직후 "저장됨 ✓"이 사라지면 안 되므로.

## 상용 UX 고도화 기준 (P14~P25 — 2026-08-23 사용자 지시로 확장)

P1~P13 이 **기능·레이아웃·일관성·사용 가능성**을 지킨다면, P14~P25 는 그 위에서
**인지부하·행동 흐름·피드백·복구성·시각적 완성도**를 본다.

| # | 기준 | 핵심 질문 |
|---|---|---|
| P14 | **3초 이해성** | 처음 본 담당자에게 3초만 보여주면 무슨 화면인지 말할 수 있는가 — 제목이 목적을 말하고, 가장 중요한 정보가 가장 먼저 보이며, 부가 정보가 핵심을 가리지 않는가 |
| P15 | **다음 행동의 명확성** (P1 강화) | Primary Action 이 **하나**인가, 주요 버튼이 서로 경쟁하지 않는가, 이름만 보고 결과를 예측할 수 있는가. 화면마다 "가장 먼저 해야 할 행동"을 한 문장으로 적어 본다 |
| P16 | **인지부하 최소화** | 다른 화면의 값을 기억하게 하거나, 같은 정보를 반복 입력하게 하거나, 파일명·id·경로를 직접 치게 하거나, 의미 모를 옵션을 늘어놓지 않는가 — "사용자가 기억하지 말고 화면이 보여준다" |
| P17 | **기본값 품질** | 아무것도 바꾸지 않고 실행해도 상용 서비스처럼 보이는 결과가 나오는가 (기본 선택·정렬·필터·크기·음성·버튼 상태) |
| P18 | **상태 전이 완성도** | Idle→Loading→Success→Error→Empty→Disabled 가 전부 정의돼 있는가 — 로딩 중 할 일, 성공 즉시 인지, 실패 원인 이해, 재시도 경로, 중복 클릭 차단 |
| P19 | **피드백 즉시성** | 클릭·저장·삭제·선택·재생·생성·이동 직후 상태 변화가 보이는가 — **"눌렀는데 아무 변화 없음" 금지** |
| P20 | **오류 예방** | 오류를 내고 설명하지 말고 애초에 못 내게 — 범위 강제·필수값 차단·형식 검증·삭제 확인·미저장 경고·중복 실행 방지 |
| P21 | **오류 복구성** | 실수한 사용자가 스스로 되돌릴 수 있는가 — 취소·재시도·원복. "처음부터 다시 해야 한다"면 개선 후보 |
| P22 | **시각적 위계** | 크기·위치·굵기·간격만 봐도 중요도(화면 목적→핵심 정보→주요 행동→보조→고급→위험)가 구분되는가 — 모든 버튼이 똑같이 강조되거나 위험 버튼이 일반처럼 보이면 위반 |
| P23 | **화면 밀도** (P3·P12·P13 보완) | 빈 공간이 **의미 있는 여백**인지 **콘텐츠 부족**인지 판단한다 — 관련 요소는 가깝게, 다른 그룹은 충분히 떨어지게, 카드가 불필요하게 쪼개지지 않게 |
| P24 | **실제 사용 시나리오** | 정적 캡처가 아니라 흐름으로 — ①정상(진입→입력→실행→확인) ②초보자(설명 없이 첫 행동→완료) ③실수(잘못 입력→오류→수정→재실행→완료) 3개를 실제로 돌린다 |
| P25 | **"싸구려 UI" 탐지** | 기능이 정상이어도 개발 중처럼 보이는 것 — 어색한 문구·과장된 버튼·다른 버튼 높이·미세한 여백 차이·정렬 어긋남·불필요한 테두리·과한 색·의미 없는 아이콘·기본 위젯 티·어색한 툴팁·레이아웃 점프·비어 보이는 카드·개발자용 티. "이 캡처를 고객에게 보여줘도 되는가?" |

### 회차별 추가 질문 (P-체크 대조 후 반드시 답한다)

1. 처음 보는 사람이 3초 안에 화면 목적을 이해하는가?
2. 첫 번째로 눌러야 할 버튼이 명확한가?
3. 사용자가 기억해야 하는 정보가 있는가?
4. 기본값만으로도 좋은 결과가 나오는가?
5. 클릭 → 처리 → 완료의 상태 변화가 명확한가?
6. 오류를 미리 예방하고 있는가?
7. 실수했을 때 쉽게 복구할 수 있는가?
8. 정보의 중요도가 시각적으로 구분되는가?
9. 초보자가 설명 없이 완료할 수 있는가?
10. 기능은 정상이어도 개발 중인 제품처럼 보이는 부분이 없는가?

### 수정 우선순위 — P0 → P1 → P2 → P3 순서로, P3 에 빠져 P1/P2 를 놓치지 않는다

| 급 | 뜻 | 예 |
|---|---|---|
| P0 | 사용 불가 | 동작 안 함·화면 깨짐·데이터 손실·잘못된 결과 |
| P1 | 사용자가 막힘 | 다음 행동을 모름·기능을 못 찾음·오류에서 복구 불가 |
| P2 | 사용성 저하 | 불필요한 입력·과도한 인지부하·일관성 문제·상태 피드백 부족 |

### AI 자기반문 (수정 전에 반드시)

> "내가 지금 고치려는 것은 **실제 사용자의 문제**인가, 아니면 **개발자의 취향**인가?"

- **수정하지 않는다**: 개인적으로 안 예뻐 보일 뿐 · 사용성 개선 근거 없음 ·
  디자인 시스템(08_qt-style)과 충돌 · 큰 구조 변경 필요(→ 10_ux-plan 제안으로)

  실수하기 쉬움 · 복구가 어려움 · 같은 개념의 UI 가 화면마다 다름 ·
  화면이 개발자용 도구처럼 보임
