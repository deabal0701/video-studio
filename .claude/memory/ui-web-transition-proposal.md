# UI 웹 전환 제안 — 2026-08-23 검토 (상태: 사용자 결정 대기, D13 수정 사안)

**배경:** 첫 실사용(골프채 영상 완주)에서 UI 결함이 연달아 나왔다 — AI 실패 사유 삼킴,
LLM 대기 중 진행 표시 없음("멈춘 줄 알았다"), 검수 플레이어 300px 고정("작아서 볼 수 없다"),
헤더 버튼 혼란(검수 화면의 빌드/TTS만/합성만). 사용자가 "PySide6 한계 아닌가, 웹 전환을
제안하라"고 요구했다.

**진단 (합의된 사실):**
- 오늘 결함 대부분은 스택이 아니라 **설계 결정의 문제** — 웹이었어도 같은 실수는 같은 결과.
- 단 미디어 UI 는 웹이 구조적으로 유리 — `<video controls>` 는 시크바·전체화면·배속이
  기본값, Qt 는 전부 수제(오늘 전체화면을 손으로 구현). 09/10 점검 대장의 상당수가
  Qt 특유 세금(QSS 애니메이션 죽음·고정 크기·팔레트·이모지)이었다.
- 이 앱은 이미 웹 콘텐츠 파이프라인 — 모션이 HTML, 엔진이 Chromium 렌더, 프리뷰가
  QtWebEngine. 상용 전환 계획(웹 서비스)과도 방향이 같아 웹 화면 투자는 버려지지 않는다.

**제안 (Claude 권장):** 화면을 웹 기술로 **화면 단위 점진 전환**, 껍데기는 지금 앱
(QtWebEngine) 유지 — 겉은 같은 설치형 앱(D12 무위반), 속은 웹. core 호출은 QWebChannel
브리지(HTTP 없음, D13 정신 유지). **반대:** FastAPI+브라우저 부활(서버·포트가 담당자
지원 업무가 됨), Electron/Tauri(런타임 하나 더).

**실행 순서(안):** ③ 검수(1~2일) → 대시보드+위저드(2~3일) → ④ 배포·설정(1~2일) →
② 대본 에디터(4~5일, 최난이도라 마지막). 합계 약 1.5~2주, 전환 중에도 앱 사용 가능.
진행 시 00_overview 결정 표에 D13 수정으로 기록해야 한다.
